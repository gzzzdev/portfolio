# 신청 도메인 요구사항

설문·퀴즈·투표·수업·행사와 그에 대한 신청·문항·응답이 **무엇을 할 수 있어야 하는가**를 적는다.
테이블·FK·클래스 구조는 적지 않는다 — 그건 이 문서를 읽고 정하는 것이다.

용어는 구조를 전제하지 않도록 골랐다. **「신청받기」**는 어떤 것을 신청 가능하게 만드는
성질을 가리키는 말이고, 그것이 별도의 행인지 콘텐츠 자신의 칸인지는 §9.1에서 정한다.

「구현 메모」로 표시된 줄은 요구사항이 아니라 **지금 코드가 그걸 어떻게 풀고 있는지**다.
새 설계가 같은 방법을 쓸 이유는 없고, 다만 그 요구가 실재한다는 증거로 남긴다.

---

## 1. 행위자

| | 할 수 있어야 하는 것 |
|---|---|
| 운영자 | 다섯 종류를 만들고 고친다. 신청을 받고 명부를 본다. 응답을 집계하고 채점 결과를 본다 |
| 회원 | 목록·상세를 보고, 신청하고, 문항에 답한다. 자기 신청과 자기 결과를 본다 |
| 비회원 | 목록·상세를 본다. 신청자 명부와 문항의 정답은 볼 수 없다 |

- 비회원에게 신청 건수는 보여야 한다(정원 마감 표시). 신청자가 **누구인지**는 보이면 안 된다.
- 응시 중인 사람에게 정답이 내려가면 안 된다.
- 구현 메모: `_basics/공개필드s.ts` 가 테이블별 화이트리스트로 두 가지를 막는다.
  문항에서 `answerKey` 제거, 신청에서 `memberId` 제거(`status` 는 취소분을 정원에서 빼려고 남긴다).

## 2. 다루는 것

다섯 종류가 공통으로 갖는 것 — 제목 · 한 줄 요약 · 본문 · 대표 이미지.

- 요약은 목록 카드에서 두 줄로 잘린다. **서식이 들어가면 안 되는 자리**다.
- 본문은 상세에서만 펼쳐지고 서식을 받는다.
- 대표 이미지가 없을 때 카드가 비지 않아야 한다.
- 구현 메모: 요약은 평문, 본문은 마크다운(`<MDC>`). 이미지가 비면 저장 시 제목·요약으로
  자동 생성하고(4~5초, 실패는 삼킨다), 그래도 없으면 종류별 기본 그림으로 떨어진다.

종류별로 더 갖는 것:

| 종류 | 자기 것 |
|---|---|
| 설문 | 구분(사전 / 사후 / 만족도 / 기타) |
| 퀴즈 | 합격 기준 점수, 허용 응시 횟수(0 = 무제한) |
| 투표 | 익명 집계 여부 |
| 수업 | 기간, 장소, 구분(학기 / 수업), 담당 강사, 학기 > 수업 **한 겹** |
| 행사 | 기간, 장소, 구분(일반행사 / 학술대회 / 세션), 학술대회 > 세션 **한 겹** |

- 퀴즈의 만점은 문항 배점의 합이다. 두 곳에 적으면 어긋난다.
- 묶음은 한 겹까지다. 학기 > 수업 > 차시 같은 두 겹은 요구에 없다.

## 3. 신청받기

신청을 받으려면 있어야 하는 값 — 신청 기간 · 사용 기간 · 요금 구분(무료 / 유료)과 금액 ·
정원 · 공개 상태(준비중 / 공개 / 비공개 / 완료).

- **신청 가능 판정은 한 문장이어야 한다.** 공개됨 && 기간 내 && 정원 미달.
  버튼을 막는 조건과 막힌 이유로 보여주는 문장이 같은 자리에서 나와야 한다.
- 신청 기간과 실제로 열리는 기간(수업·행사의 일정)은 **다른 값**이다. 상세 화면이 둘을 섞으면 안 된다.

## 4. 신청

한 건은 **회원 × 신청받는 것**이다.

- 같은 사람이 같은 것에 두 번 신청할 수 없다.
- 진행 단계 — 접수 / 확정 / 취소. 취소된 건은 정원에서 빠진다.
- 신청 한 건의 결제 상태를 알 수 있어야 한다.
- 구현 메모: 결제 상태를 신청에 열로 두지 않고 결제 쪽에서 읽는다. 복사해 두면 둘이
  어긋났을 때 어느 쪽이 맞는지 판정할 근거가 없다.

## 5. 질문지와 문항

질문지는 문항의 묶음이고, 익명 집계 여부를 갖는다.
설문 본문이든 행사 신청서든 **같은 것으로 쓴다**.

문항 하나가 갖는 것 — 순번 · 문두 · 유형 · 선택지 · 정답 · 배점 · 필수 여부.

- 유형은 여섯 — 단답 / 서술 / 객관식(1개) / 객관식(여러 개) / OX / 척도.
  선택지를 쓰는 건 객관식 둘 · OX · 척도다.
- **순번이 화면 정렬의 유일한 기준이다.**
- 정답이 있으면 채점 문항, 없으면 아니다. 채점 여부를 따로 켜고 끄는 값을 두지 않는다.
- OX의 선택지는 사람이 지우거나 바꿀 수 없어야 한다.
- 정답이 선택지 밖을 가리키면 저장을 막아야 한다. 통과시키면 채점이 조용히 전부 오답이 된다.
- 합격선이 만점보다 높으면 저장을 막아야 한다.

## 6. 응답과 채점

응답 한 칸은 **신청 × 문항 × 회차**다.

세 가지가 되어야 한다. 셋 다 실제로 필요해서 적는다.

1. **부분 저장** — 다 못 채운 채 나갔다 돌아와도 쓴 것이 남는다
2. **문항별 집계** — "3번 문항의 선택지별 응답 수"를 셀 수 있다
3. **정답만 빼고 내려보내기** — 응시자에게 갈 때 정답이 빠진다

- 구현 메모: 셋을 동시에 만족시키려고 응답과 문항을 각각 행으로 둔다.
  문항이 질문지 안의 JSON 배열이면 3번이 불가능하다(통째로 나간다).
- **회차** — 재응시하면 회차가 는다. 앞 회차 응답은 남고, 점수는 이번 회차 것만 센다.
- 필수 문항에 다 답하지 않으면 제출을 막고, **무엇이 남았는지 목록으로** 보여준다.
- 익명은 **표시상**이다. 결과 화면에서 응답자를 가릴 뿐, 신청 기록은 남는다.
  안 남기면 중복 응답을 막을 방법이 사라진다.
- 채점 결과는 회차별로 점수 · 만점 · 합격선 · 합격 여부 · 문항별 정오를 갖는다.

## 7. 목록과 검색

- 다섯 종류를 **한 목록에서** 보고 종류로 걸러낼 수 있어야 한다.
- 종류의 이름과 아이콘은 한 곳에서만 정해져야 한다. 화면마다 따로 적으면 같은 것을
  화면마다 다르게 부르게 되고, 그때 검색어 「종류=설문」이 어느 화면에서는 안 걸린다.

## 8. 현재 데이터 실측 (2026-09-08, `_CUSTOM/localDB`)

정하기 전에 참고할 사실. 판단이 아니라 센 값이다.

- 신청받기 14건 — **대상 하나당 정확히 1건.** 2건 이상인 대상 없음
- 질문지 11건 — 신청받기 11건과 1:1. 공유 0건, 아무도 안 가리키는 질문지 0건
- 신청받기 14건 중 3건은 질문지가 없다(수업 1, 행사 2)
- 문항 27개, 질문지당 1~4개
- 수업 3건 = 학기 1 + 그 아래 수업 2. 행사 4건 = 학술대회 1 + 세션 2 + 단독 행사 1
- 「2026학년도 1학기」(학기)에도 신청받기가 1건 열려 있고, 질문지는 없다

## 9. 미결 — 유연 ↔ 엄밀

일곱 건 모두 **아직 안 정했다.** 각 항목의 두 끝과 그 끝을 골랐을 때 무엇이 어려워지는지만 적는다.
정해지면 해당 항목을 지우고 결론을 이 문서 위쪽 본문에 한 줄로 옮긴다.

### 9.1 「신청받기」가 콘텐츠 자체인가, 콘텐츠에 붙는 것인가

- **유연** — 별개로 존재하고 콘텐츠 하나에 0..N개 붙는다.
  난이도: 생명주기가 둘이 된다. 「아직 신청받기가 안 붙은 콘텐츠」 상태가 모든 화면·집계에
  상시 등장한다. N개일 때 "이 콘텐츠의 문항"처럼 하나를 골라야 하는 자리마다 대표 선택 규칙이 필요하다.
- **엄밀** — 콘텐츠가 곧 신청받는 것이다. 만들면 그 순간 존재한다.
  난이도: 9.2가 강제로 딸려온다. 신청 관련 칸이 다섯 종류 전부에 항상 존재한다.

### 9.2 신청을 받지 않는 콘텐츠가 있는가

읽히기만 하는 수업 소개, 명부 없는 공지용 설문 같은 것.

- **유연** — 허용한다.
  난이도: 화면이 「신청 가능」과 「읽기 전용」 두 모드를 갖는다. 신청 버튼 · 정원 · 기간 표시가 전부 조건부가 된다.
- **엄밀** — 모든 콘텐츠는 신청 대상이다.
  난이도: 읽기만 하는 글은 이 도메인 밖(게시판 등)으로 보내야 하고, 그 경계 규칙을 세워야 한다.

### 9.3 질문지를 여러 콘텐츠가 돌려쓰는가

같은 만족도 문항을 수업 세 개에 붙이는 경우.

- **유연** — 공유한다.
  난이도: 집계가 「어느 콘텐츠에서 받은 응답인가」를 따로 갈라야 한다. 질문지를 고치면 이미
  응답을 받은 다른 콘텐츠까지 바뀐다 — 그 시점 이후 수정 금지 같은 규칙이 필요하다.
- **엄밀** — 질문지는 한 콘텐츠 전용이다.
  난이도: 같은 문항을 반복 입력하게 되므로 복제 기능이 사실상 필수가 된다.

### 9.4 한 콘텐츠에 조건이 다른 창구를 둘 이상 두는가

얼리버드 / 일반, 회원가 / 비회원가처럼 요금·기간만 다른 창구.

- **유연** — 둘 이상 둔다.
  난이도: 정원이 창구별인지 합계인지 정의해야 한다. 중복 신청 판정 단위가 창구인지 콘텐츠인지
  정해야 한다. 질문지가 창구별인지 공유인지도 갈린다(9.3과 얽힌다).
- **엄밀** — 콘텐츠당 하나다.
  난이도: 요금이 갈리면 콘텐츠를 나눠야 하고, 제목·본문·이미지가 복제된다.

### 9.5 상위(학기 · 학술대회)도 신청을 받는가

- **유연** — 받는다.
  난이도: 상위 신청과 하위 신청의 관계를 정의해야 한다. 학기에 신청하면 그 아래 수업이
  자동인지, 별개인지, 정원과 명부를 둘 다 세는지.
- **엄밀** — 상위는 묶음일 뿐이고 신청은 말단에서만 받는다.
  난이도: 「학기 등록」처럼 상위 단위의 등록 업무가 실제로 있으면 표현할 수 없다.

### 9.6 다섯 종류가 정말 다섯인가

설문 · 투표 · 퀴즈의 차이는 **정답이 있는가**와 **익명인가** 둘뿐이다.
수업 · 행사의 차이는 담당 강사 하나와 구분 값뿐이다.

- **유연** — 종류를 줄이고 성격을 값으로 둔다.
  난이도: 메뉴 · 목록 · 권한이 종류별로 갈려 있다면 그 축을 값으로 다시 세워야 한다.
  화면 어휘(응답 / 참여 / 응시)도 값에서 나와야 한다.
- **엄밀** — 다섯을 각각 그대로 둔다.
  난이도: 공통 부분이 계속 복제되거나 상속 계층이 필요하다. 종류가 하나 늘 때마다 같은 작업을 반복한다.

### 9.7 비회원이 신청하거나 응답할 수 있는가

- **유연** — 할 수 있다.
  난이도: 중복 방지 수단을 회원 대신 무엇으로 할지 정해야 한다(이메일 · 토큰 · 기기).
  명부와 집계에서 동일인 판정이 불가능해진다. 유료일 때 결제·환불 주체가 불분명해진다.
- **엄밀** — 회원만 할 수 있다.
  난이도: 공개 설문이나 가입 전 사전등록처럼 회원가입을 요구할 수 없는 업무는 받을 수 없다.
